## 3. Population reconciliations

**2,000 customer records → 1,991 active customers.** Not a data loss.

| Step | Count |
|---|---|
| Customer records in `customers.csv` | 2,000 |
| Appear in `orders.csv` | 1,999 |
| Have at least one Delivered/Processing order | 1,991 |
| Only Cancelled/Returned orders | 8 (4 Returned, 2 Cancelled, 2 both) |
| Never ordered | 1 |

1,991 is the revenue-eligible customer population used by RFM, CLV, and the churn
feature table. The 9 excluded customers are disclosed in the data-quality report.

**12,000 placed orders → 9,933 eligible orders.** 621 Processing are booked but not
fulfilled. Including them is a deliberate basis choice, stated in every figure; on a
Delivered-only basis revenue is ₹55.49 Cr, not ₹59.28 Cr.

**10.19% vs 11.61%.** The first is Returned ÷ all 12,000 placed orders. The second is
Returned ÷ (Delivered + Returned) = 1,223 ÷ 10,535, i.e. returns among orders that
reached a terminal state. Both are correct with their denominators named; the README
uses the first.

**53.97% vs 53.79%.** Headline margin is value-weighted: profit ÷ revenue = 53.9733%.
The discount curve uses the unweighted mean of line-level margin rates, which is
53.79% at 0% discount. Zero-discount aggregate margin is 56.67% and discounted
aggregate is 51.96% — the gap is product/order mix, not an arithmetic error.

## 7. What this repo does not claim

- Not real customer data. The generator is seeded; every number is illustrative.
- Not causal. Discount, churn, and CLV results are observational.
- Not a production ML system. No live inference, no monitored model, no campaign run.
- Not a general NL-to-SQL accuracy claim. 97.3% is 36 of 37 questions on one benchmark.
- Not a classic BCG matrix. It is a median-units vs median-margin proxy.

## 11. Defect found and fixed during verification

Navigating Pricing Lab → Win-Back raised
`Canvas is already in use. Chart with ID '4' must be destroyed before the canvas
with ID 'ch_pricing_margin' can be reused.`

Cause: `buildPricing()` runs at `DOMContentLoaded` and again from both the `pricing`
and `winback` nav branches, and it builds `ch_pricing_margin` plus `ch_winback_sens`
without checking whether they already exist.

Fix: an idempotence guard in `scripts/pricing_dashboard_templates.py` — the source
of truth for the injected block — rather than patching individual charts:

```js
let _pricingBuilt = false;
function buildPricing(){
  if (_pricingBuilt) return;
  _pricingBuilt = true;
  ...
}
```

The injector regenerated all four deployment copies (SHA256
`83BD5037B09679A649046931B61D93C5987BE6F66C6FBF3913A855D3F06A0B41`). Re-test:
Pricing → Win-Back → Pricing → Win-Back → Overview → Pricing, 0 console errors,
both canvases still hold live Chart.js instances.

Mobile check: headless Chrome clamps its window to 512 px, so a 390 px capture is a
crop of a 512 px layout, not evidence of overflow. At 512 px the layout is clean —
2-column KPI grid, no clipped cards, header pills fit.

### FastAPI endpoint: accuracy defect found and fixed

Live probing of `POST /api/v1/query/nl-to-sql` before the fix: 6 of 10 questions
returned the same order-status distribution — including "What is the meaning of
life?" and "What is the weather tomorrow?" — all flagged `is_safe: true`. The old
`else` branch answered every unmatched question with status counts. That is a
silent wrong answer, and it violated the repo's never-fabricate rule.

Fix in `app/services/query_service.py`:

- removed the catch-all fallback; unmatched questions return
  `generated_sql: ""`, `row_count: 0`, `data: []`, explanation starting `Refused:`;
- added grounded intents for total revenue, total profit, total orders, total
  customers, overall margin, margin by category, revenue by region, and order-status
  distribution;
- added a scope guard so a question naming an unsupported dimension or period
  ("revenue by customer segment", "revenue in 2024") is refused instead of answered
  at the wrong grain.

Re-verified against the seeded DB: revenue 59,283,619.32; profit 31,997,341.64;
orders 9,933; customers 1,991; margin 53.97%; West the top region; Sports 56.5%
margin; status counts 9,312 / 1,223 / 844 / 621. Off-scope questions now refuse.

Pinned by `tests/api/test_nl_query_accuracy.py` (aggregates compared to a direct SQL
reference on the same database, plus refusal assertions), so the fallback cannot
return. `docs/API_DOCUMENTATION.md` was corrected: actual path
`/api/v1/query/nl-to-sql`, payload `{"question": ...}`, supported scope and refusal
behavior documented, and the 97.3% figure attributed to `scripts/nl_to_sql.py`
rather than to this endpoint.
